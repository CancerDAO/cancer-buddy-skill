# i18n — Shared Locale Layer

This is the single locale contract for the **entire `cancer-buddy` skill family** (every patient-visible sub-skill: organize / mind / caregiver / disclosure / education / nutrition / find-care / second-opinion / visit-prep / vault, and the meta `cancer-buddy` router). All of them read this file. The rule is one resolved locale, one persisted value, reused for the whole patient journey.

The core invariant: **localize the scaffold, never the clinical entity.** Drug names, gene symbols, variants, TNM/stage strings, numbers and units stay verbatim in their source form; only section titles, narrative connectives, field labels, user-facing copy and date formats follow the locale. Mistranslating a clinical entity is a P0 medical-safety bug (see `safety-guardrails.md` → "Clinical entities are never translated").

## 1. What is `locale`

A BCP-47 language tag — `en`, `fr`, `es`, `zh`, `de`, `pt`, `ar`, … — describing the language the **patient-facing scaffold** is rendered in. It is NOT a claim about the language of the clinical content (records may be multilingual; clinical entities stay verbatim regardless of locale).

## 2. Resolution priority

Locale is resolved in this order:

1. **Host-supplied `locale` parameter**: if the caller / product host supplies a valid BCP-47 `locale` (or equivalent call field such as `ui_language`) from the user's explicit product language setting, use it immediately for the current run. This is an explicit user preference, not arbitrary platform inference. It wins over `profile.json.locale`, record language, conversation language, and all auto-detection. Forward it unchanged to any child sub-skill. If `profile.json` is written or updated during the run, persist `profile.json.locale = "<locale>"`.
2. **Persisted `profile.json.locale`**: when no host `locale` is supplied, read `profile.json.locale` first. If present, use it — do not re-detect.
3. **Auto-detection fallback**: only when neither a host `locale` nor a persisted locale exists, detect by sub-skill type as below.

| Sub-skill type | Detection source |
|---|---|
| `cancer-buddy-organize` | the **primary patient-facing language of the medical records** (the language most of the narrative / clinical documents are written in). |
| record-consuming generative sub-skills (`education` / `nutrition` / `second-opinion` / `visit-prep` / `vault`) | **reuse `profile.json.locale`** (they run after organize, so it is normally already persisted). When no profile exists yet, fall back to the **primary patient-facing language of the records**, tie-breaking to the user's conversation language. |
| chat sub-skills (mind / caregiver / disclosure / find-care / …) | the **language the user is conversing in** (the current input). |
| meta `cancer-buddy` router | when no host `locale` is supplied and no profile exists, the language of the user's opening message — used **only** for the pre-routing reply; a **temporary value the router does NOT persist**. On the organize path, if no host `locale` was supplied, the canonical locale is written later by organize (`cb-organizer`) from the records' primary language (§3) and may correct this provisional value (e.g. an English caregiver about Chinese records). |

### 2.1 Mixed-language records / conversation

When the input mixes languages (e.g. an English discharge summary with Chinese physician notes, or a user typing 中英 mixed):

1. Take the **primary patient-facing language** — the language the majority of the *narrative / clinical-document prose* is in (count narrative weight, not stray tokens; a Chinese report with English drug names is still `zh`).
2. **Tie-break**: when narrative weight is genuinely even, fall back to the **language the patient themselves writes / speaks in** (their own free-text, diary entries, or chat turns) — the scaffold should speak the patient's own language, not the institution's.

This is an LLM judgment over the actual content — do **not** run a hardcoded keyword/character-set language table. Read the records / conversation and decide.

## 3. Persist & reuse (`profile.json.locale`)

- When the host supplies `locale`, **write / update** `profile.json.locale` to that BCP-47 tag whenever the run writes profile state. Treat this as an explicit user language override.
- On first detection fallback, **write** the detected BCP-47 tag to `profile.json.locale` (the `cb-organizer` subagent is the canonical writer; a chat sub-skill that detects locale before any organize run may write it if no profile exists yet, then organize honors it unless a later host `locale` explicitly overrides it).
- On every subsequent sub-skill entry with no host `locale`: **read `profile.json.locale` first**. If present, use it — do not re-detect (guarantees one consistent scaffold language across the whole patient journey).
- Only when no host `locale` is supplied and `profile.json` is absent (or `locale` is null) does a sub-skill detect from the current input.
- **Sanctioned exception — reviewer-facing artifacts:** `cancer-buddy-second-opinion` produces packets read by an *international reviewer*, not the patient, so it may render that reviewer-facing artifact in a separate `reviewer_locale` (e.g. English for an MSK/MD Anderson packet) while the patient-facing journey stays in `profile.json.locale`. This is the ONE place two locale axes legitimately coexist; clinical entities stay verbatim in both. No other sub-skill introduces a second locale axis.
- The user may override at any time ("answer me in English" / "用中文") → update `profile.json.locale` and honor going forward. An explicit user override always wins over auto-detection.

```
host locale OR persisted locale OR detection fallback
   └─► persist  profile.json.locale = "<bcp47>"
          └─► every later sub-skill: read it, render scaffold in that locale, reuse
```

## 4. Verbatim-clinical policy

**Never translate, transliterate, or normalize a clinical entity.** Keep the source form exactly:

| Entity class | Examples (stay verbatim) |
|---|---|
| Drug names (generic + brand) | osimertinib, 奥希替尼 (whichever the source used), Tagrisso, 卡铂 |
| Genes / variants | EGFR L858R, KRAS G12C, ALK fusion, BRCA1 c.68_69delAG |
| Stage / TNM / response | cT3N2M0, IIIA, ypT2N1, RECIST PR, MSI-H |
| Numbers + units | CEA 12.4 ng/mL, eGFR 58 mL/min, 80 mg qd, 2.1 cm |
| Biomarker labels | PD-L1 TPS 40%, TMB 11 mut/Mb, Ki-67 60% |

Only the **scaffold** is localized — section titles, narrative connectives ("diagnosed with" / "确诊"), field labels, disclaimers, user prompts, diff cards, routing copy, date formats.

**Optional gloss, not replacement:** a locale-appropriate plain-language explanation may be added *beside* the verbatim term in parentheses (handled by `terminology.md`), but the source term is never removed or swapped. e.g. `osimertinib (third-generation EGFR TKI)` — the drug name stays, the gloss is localized.

## 5. How to localize the scaffold

Two mechanisms, pick per artifact type:

- **Template / form / questionnaire / handbook artifacts** (段D case-summary HTML, education manuals, mind screening instruments, second-opinion packet, diff cards): extract a **locale → string table** (section titles, labels, disclaimers, "to be supplemented" placeholders keyed by string id). The HTML/CSS/structure stays 1:1; only the string values come from the table. Never hardcode a single-language string into the template.
- **Narrative / generative output** (病情概要 narrative, chat replies, review_summary prose): the prompt instruction carries **"Output all scaffold/narrative prose in `<locale>`; keep clinical entities verbatim per `references/i18n.md` §4."** The subagent writes directly in the target locale.

Do not encode language-specific phrasing as a hardcoded Python keyword/phrase list — the only fixed mapping allowed is the bucket-name table below (§6), which is a stable filesystem key, not prose.

## 6. organize — bucket folder localization

**Folder-slug policy (two pinned sets, never per-language).** On-disk folder slugs are infrastructure keys, not user-facing prose. They come in **exactly two pinned forms**: `zh` (when `locale=zh`) and `en` (**every other locale** — fr/es/de/pt/ar/… all use the `en` slugs, NOT a runtime-translated French/Spanish/German name). Both top-level domains (§6.1) and typed subdirs (see `skills/cancer-buddy-organize/references/bucket-taxonomy.md §1.1a`) are fully pinned in these two sets; they are **NOT generated per-language**. The **`NN_` two-digit prefix is a language-independent stable key.** Downstream anchors and consumers match on the `NN_` numeric prefix (anchor regex `^[0-9]{2}_…`), never on the localized name — so the pinned slug never breaks anchor resolution, `_FILENAME_MAPPING`, or any bucket-relative `[[src:…]]`. All user-facing text (timeline prose, summaries, INDEX labels, UI) still localizes in the patient's locale; only the folder **names** are restricted to the two pinned sets.

### 6.1 locale → bucket-name map

`zh` = the canonical Chinese folder names. `en` = canonical English slugs. The `NN_` prefix is identical across locales. **Authoritative scheme = `skills/cancer-buddy-organize/references/bucket-taxonomy.md` (scheme_version 3)**; this table must match it.

| NN_ key (stable) | `zh` | `en` (canonical slug) |
|---|---|---|
| `01_` | `01_身份与基础信息` | `01_identity_basics` |
| `02_` | `02_既往史与家族史` | `02_history_family` |
| `03_` | `03_病程与叙事文书` | `03_clinical_notes` |
| `04_` | `04_诊断与分期` | `04_diagnosis_staging` |
| `05_` | `05_影像` | `05_imaging` |
| `06_` | `06_分子与组学` | `06_molecular_omics` |
| `07_` | `07_检验` | `07_labs` |
| `08_` | `08_治疗` | `08_treatment` |
| `09_` | `09_手术与操作` | `09_procedures` |
| `10_` | `10_随访与监测` | `10_followup_monitoring` |
| `11_` | `11_会诊与转诊` | `11_consult_referral` |
| `12_` | `12_心理社会与支持` | `12_psychosocial_support` |
| `13_` | `13_行政与财务` | `13_admin_financial` |
| `14_` | `14_患者自管补充` | `14_patient_supplement` |
| `raw/` | `raw` | `raw` |
| `99_` | `99_无关文件` | `99_unrelated` |

`01_`…`14_` are the visible clinical domains; `raw/` (verbatim vault of every uploaded original — locale-independent ASCII name, never localized) and `99_` (relevance quarantine) are hidden infrastructure, never anchored.

Typed subdirectories under a bucket (`04_诊断与分期/病理报告`, `05_影像/PET-CT`, `06_分子与组学/WES-WGS`, `10_随访与监测/可穿戴导出`, `99_无关文件/high_confidence`, `99_无关文件/uncertain`) follow the same two-pinned-sets rule: the parent `NN_` prefix is stable; the subdir slug is `zh` (when `locale=zh`) or `en` (every other locale), **fully pinned** in `skills/cancer-buddy-organize/references/bucket-taxonomy.md §1.1a` — never runtime-translated into another language. `high_confidence` / `uncertain` / `conversation_notes` are already ASCII keys and stay as-is across locales.

### 6.2 Non-`zh` locales use the pinned `en` slugs (no per-language generation)

Folder slugs are `zh` (when `locale=zh`) or `en` (all other locales), both **fully pinned** (domains §6.1, subdirs see `skills/cancer-buddy-organize/references/bucket-taxonomy.md §1.1a`); they are **NOT generated per-language**. A `fr`/`es`/`de`/`pt`/… patient gets the **`en` folder slugs** (e.g. `04_diagnosis_staging/pathology`), with the `NN_` prefix kept verbatim — there is no runtime French/Spanish/German slug generation (that runtime generation was the cross-run drift source and is removed). User-facing text still localizes in prose/labels/INDEX/UI, **not** in folder names. Downstream still matches on `NN_`.

## 7. Quick checklist for any sub-skill

1. If caller supplies `locale`, use it, forward it to child sub-skills, and persist it when profile state is written.
2. Otherwise read `profile.json.locale`; if absent, detect (§2) and persist (§3).
3. Render every patient-visible scaffold string in that locale (§5).
4. Keep every clinical entity verbatim (§4).
5. (organize only) Name buckets per §6, prefix `NN_` stable.
6. Honor an explicit user language override and write it back.
