# 病例报告

帮用户看看文献里有没有情况相近的病例报告，以及这些报告能说明什么、不能说明什么。

## 读什么

`profile.json`（癌种、病理、关键变异、治疗经过）；需要细节时读 `molecular.json`、`treatment_lines.json`。按 [archive.md](../cancer-buddy/references/archive.md) 读。先和用户确认检索的关键特征（如"肺腺癌 + EGFR exon20 插入"）。

## 默认给精简版

v1 第一次真实使用花了 25 分钟、输出 454 行，家属读不下去。所以默认：

- **最多 5 例**，一张表，加几句话总结，几分钟内给出。
- 用户说"展开""更多""详细"，再扩大检索、逐例细讲，并写到 `<patient_dir>/reports/case-precedent/`。

## 精简版的结构

1. **检索记录**（两三行）：查了哪些库、检索词、日期、命中多少、为什么挑这几例。
2. **逐例事实表**：文献标题 + PMID/DOI、患者概况、治疗、报告的结局、随访时长。按发表时间等中性顺序排列。
3. **相同 / 不同 / 不知道**：每例和本人比，哪些特征一样、哪些不一样、哪些报告里没写。
4. **偏倚提醒**：病例报告倾向于发表"效果好"或"罕见"的案例；一例或几例说明不了一般规律，也说明不了用在本人身上会怎样。
5. **可以问医生的问题**：两三个中立的问题，如"这篇报告里的做法，和我的情况有哪些关键不同？"

## 边界

- 不算相似度分，不按"最像"排序。
- 不从几个病例里算有效率、中位生存。
- 结局不好的病例同样列出，不淡化。
- 核对撤稿状态；留意同一个病人被多篇文章重复报道。没查的不说"已排除重复"。
- 不说"你也可以试这个方案"。

## 语气

对家属：先说一句"病例报告是线索，不是答案"，再给表格。结局不好的病例要如实写，但措辞平实。
